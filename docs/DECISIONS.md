# 設計判断の記録

仕様書：[SPEC.md](SPEC.md) ／ ロードマップ：[ROADMAP.md](ROADMAP.md) ／ ワークフロー：[WORKFLOW.md](WORKFLOW.md)

なぜそう決めたかを残す。
決定を変えるときは、元の記述を消さず、変更の理由を追記する。

各項目は「決定」「理由」「できなくなること」を持つ。
「決定者」は、ユーザーが選んだものを「ユーザー」、アシスタントが決めて通知したもの（WORKFLOW 2.2）を「アシスタント」とする。

## 前提（着手前に決めたもの）

### D-001：ターゲットは RISC-V 64（RV64GC）、QEMU の `virt` マシン

- 決定者：ユーザー
- 理由：仕様が小さく、学習の本題でない仕組み（x86 のセグメント、レガシーな割り込みコントローラ、リアルモードからの移行）に時間を取られない。参照先の xv6-riscv がそのまま使える
- できなくなること：x86_64 向けの豊富な資料（blog_os、MikanOS）を直接は使えない。手元の PC の実機では動かない。実機での確認は M7 以降、RISC-V ボードを用意したときに限られる

### D-002：起動は OpenSBI に任せ、カーネルは S モードから始まる

- 決定者：ユーザー
- 理由：QEMU に同梱の OpenSBI がそのまま使える。実機の RISC-V（Linux が動くボード）と同じ構成であり、M7 で実機に移るときの差が小さい
- できなくなること：M モードの初期化（`mstatus`、`medeleg`、PMP の設定）を自分では書かない。xv6 の `start.c` に当たる学習は省かれる。タイマーや文字出力の一部は SBI の呼び出しを経由することになる

### D-003：到達目標はユーザーランドと簡易シェル（M6）

- 決定者：ユーザー
- 理由：システムコールとユーザープロセスまで作ると、カーネルの本質（保護、トラップ、アドレス空間の分離）を一通り通る
- できなくなること：ファイルシステムとディスクは第 1 段階に含めない。ユーザープログラムはカーネルイメージに埋め込む（M5）

### D-004：参照先は xv6-riscv。構造を参照し、コードは写さない

- 決定者：ユーザー
- 理由：教育用に書かれており、解説書（xv6 book）がある。RISC-V 版があり、D-001 と一致する
- できなくなること：xv6 は C であり、所有権や型による安全性を持たない。そのまま移すと `unsafe` だらけになる。Rust の型で表し直す設計の手間は、こちらで負う
- 補足：xv6 は M モードから起動するため、D-002 によって起動部分は参照できない

### D-005：外部クレートは最小限。自作を優先する

- 決定者：ユーザー
- 理由：自作する範囲が、そのまま学習の範囲になる
- 方針：
  - 起動、ページテーブル、CSR の操作、SBI の呼び出し、アロケータ、ロック、DTB と ELF の解析は自作する
  - `bitflags` のような、学習の本題でない小さな道具は、必要になった時点で検討する
  - クレートを追加するときは、その都度ここに理由を記録する
- できなくなること：`riscv`、`sbi-rt`、`buddy_system_allocator` などの既製品で時間を節約することはしない

### D-006：テストはホスト（`klib`）と QEMU（`kernel`）の 2 か所で動かす

- 決定者：ユーザー
- 理由：ハードに依存しないロジックをホストの `cargo test` で回せば、速く、突然変異テストも現実的な時間で済む。ハードとの境界は QEMU で確かめるしかない
- できなくなること：ロジックをハードから切り離すための抽象（物理メモリへのアクセスを差し替えられる形など）を、設計に組み込む必要がある。ワークスペースが 2 クレートになり、ビルドの設定が少し複雑になる

### D-007：開発環境は Windows + WSL2（Ubuntu）

- 決定者：ユーザー
- 方針：リポジトリは WSL の Linux 側のファイルシステム（`~/` の下）に置き、`/mnt/c` の下には置かない。Windows 側のファイルシステムをまたぐと、ビルドが遅く、ファイルの権限も扱いにくい
- できなくなること：Windows 側のツールからリポジトリを直接編集するのは避け、作業は WSL の中で完結させる

### D-008：hart は 1 つで始め、マルチ hart は M7 以降

- 決定者：アシスタント
- 理由：複数の hart を同時に起動すると、起動順、ロック、メモリ順序の問題が一度に出る。学習の段差として大きすぎる
- 方針：ロックと割り込み禁止は最初から正しく書く。QEMU も `-smp 1` で起動する
- できなくなること：メモリ順序（`fence`）や hart 間の競合の誤りは、M7 まで観測できない（WORKFLOW 4.4）

### D-009：Rust は stable、edition 2024

- 決定者：アシスタント
- 理由：`riscv64gc-unknown-none-elf` は `core` と `alloc` が配布されており、nightly の `build-std` なしで使える。nightly の機能は、カーネルの学習の本題ではない
- 方針：M0 の時点でインストールされている stable のバージョンを `rust-toolchain.toml` に固定する。edition 2024 の安全側の規則（`static mut` への参照の拒否、`#[unsafe(no_mangle)]`）に従う
- できなくなること：nightly 専用の機能（`custom_test_frameworks`、`naked_functions` の一部など）は使わない。QEMU 上のテストの枠組みは stable の範囲で組む。必要になったら、理由を記録して切り替える

### D-010：ワークスペースは `kernel` と `klib` の 2 クレートから始める

- 決定者：アシスタント
- 理由：D-006 を構造で表す。`klib` を `no_std` で書けば、カーネルからもホストのテストからも同じコードを使える
- 方針：`klib` は `#![cfg_attr(not(test), no_std)]` とし、テストのときだけ `std` を使う。M5 で `user/` を加える
- できなくなること：`klib` に、CSR やアセンブリなどハードに依存するコードを置いてはならない。境界がずれていないかをレビューで確かめる
