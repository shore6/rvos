# 設計判断の記録

仕様書：[SPEC.md](SPEC.md) ／ ロードマップ：[ROADMAP.md](ROADMAP.md) ／ ワークフロー：[WORKFLOW.md](WORKFLOW.md)

なぜそう決めたかを残す。
決定を変えるときは、元の記述を消さず、変更の理由を追記する。

各項目は「決定」「理由」「できなくなること」を持つ。
「決定者」は、ユーザーが選んだものを「ユーザー」、アシスタントが決めて通知したもの（WORKFLOW 2.2）を「アシスタント」とする。

---

## 前提（着手前に決めたもの）

### D-001：ターゲットは RISC-V 64（RV64GC）、QEMU の `virt` マシン

- 決定者：ユーザー
- 理由：仕様が小さく、学習の本題でない仕組み（x86 のセグメント、レガシーな割り込みコントローラ、リアルモードからの移行）に時間を取られない。参照先の xv6-riscv がそのまま使える
- できなくなること：x86_64 向けの豊富な資料（blog_os、MikanOS）を直接は使えない。手元の PC の実機では動かない。実機での確認は M7 以降、RISC-V ボードを用意したときに限られる

### D-002：起動は OpenSBI に任せ、カーネルは S モードから始まる

- 決定者：ユーザー
- 理由：QEMU に同梱の OpenSBI がそのまま使える。実機の RISC-V（Linux が動くボード）と同じ構成であり、M7 で実機に移るときの差が小さい
- できなくなること：M モードの初期化（`mstatus`、`medeleg`、PMP の設定）を自分では書かない。xv6 の `start.c` に当たる学習は省かれる。タイマーや文字出力の一部は SBI の呼び出しを経由することになる

### D-003：到達目標はユーザーランドと簡易シェル（M6）

- 決定者：ユーザー
- 理由：システムコールとユーザープロセスまで作ると、カーネルの本質（保護、トラップ、アドレス空間の分離）を一通り通る
- できなくなること：ファイルシステムとディスクは第 1 段階に含めない。ユーザープログラムはカーネルイメージに埋め込む（M5）

### D-004：参照先は xv6-riscv。構造を参照し、コードは写さない

- 決定者：ユーザー
- 理由：教育用に書かれており、解説書（xv6 book）がある。RISC-V 版があり、D-001 と一致する
- できなくなること：xv6 は C であり、所有権や型による安全性を持たない。そのまま移すと `unsafe` だらけになる。Rust の型で表し直す設計の手間は、こちらで負う
- 補足：xv6 は M モードから起動するため、D-002 によって起動部分は参照できない

### D-005：外部クレートは最小限。自作を優先する

- 決定者：ユーザー
- 理由：自作する範囲が、そのまま学習の範囲になる
- 方針：
  - 起動、ページテーブル、CSR の操作、SBI の呼び出し、アロケータ、ロック、DTB と ELF の解析は自作する
  - `bitflags` のような、学習の本題でない小さな道具は、必要になった時点で検討する
  - クレートを追加するときは、その都度ここに理由を記録する
- できなくなること：`riscv`、`sbi-rt`、`buddy_system_allocator` などの既製品で時間を節約することはしない

### D-006：テストはホスト（`klib`）と QEMU（`kernel`）の 2 か所で動かす

- 決定者：ユーザー
- 理由：ハードに依存しないロジックをホストの `cargo test` で回せば、速く、突然変異テストも現実的な時間で済む。ハードとの境界は QEMU で確かめるしかない
- できなくなること：ロジックをハードから切り離すための抽象（物理メモリへのアクセスを差し替えられる形など）を、設計に組み込む必要がある。ワークスペースが 2 クレートになり、ビルドの設定が少し複雑になる

### D-007：開発環境は Windows + WSL2（Ubuntu）

- 決定者：ユーザー
- 方針：リポジトリは WSL の Linux 側のファイルシステム（`~/` の下）に置き、`/mnt/c` の下には置かない。Windows 側のファイルシステムをまたぐと、ビルドが遅く、ファイルの権限も扱いにくい
- できなくなること：Windows 側のツールからリポジトリを直接編集するのは避け、作業は WSL の中で完結させる

### D-008：hart は 1 つで始め、マルチ hart は M7 以降

- 決定者：アシスタント
- 理由：複数の hart を同時に起動すると、起動順、ロック、メモリ順序の問題が一度に出る。学習の段差として大きすぎる
- 方針：ロックと割り込み禁止は最初から正しく書く。QEMU も `-smp 1` で起動する
- できなくなること：メモリ順序（`fence`）や hart 間の競合の誤りは、M7 まで観測できない（WORKFLOW 4.4）

### D-009：Rust は stable、edition 2024

- 決定者：アシスタント
- 理由：`riscv64gc-unknown-none-elf` は `core` と `alloc` が配布されており、nightly の `build-std` なしで使える。nightly の機能は、カーネルの学習の本題ではない
- 方針：M0 の時点でインストールされている stable のバージョンを `rust-toolchain.toml` に固定する。edition 2024 の安全側の規則（`static mut` への参照の拒否、`#[unsafe(no_mangle)]`）に従う
- できなくなること：nightly 専用の機能（`custom_test_frameworks`、`naked_functions` の一部など）は使わない。QEMU 上のテストの枠組みは stable の範囲で組む。必要になったら、理由を記録して切り替える

### D-010：ワークスペースは `kernel` と `klib` の 2 クレートから始める

- 決定者：アシスタント
- 理由：D-006 を構造で表す。`klib` を `no_std` で書けば、カーネルからもホストのテストからも同じコードを使える
- 方針：`klib` は `#![cfg_attr(not(test), no_std)]` とし、テストのときだけ `std` を使う。M5 で `user/` を加える
- できなくなること：`klib` に、CSR やアセンブリなどハードに依存するコードを置いてはならない。境界がずれていないかをレビューで確かめる

## M0

### D-011：ツールチェーンは Rust 1.99.1 に固定する

- 決定者：アシスタント（D-009 の方針の適用）
- 内容：M0 着手時（2026-11-08）にインストールされていた stable が 1.99.1 だった。`rust-toolchain.toml` の `channel` にこの版を書き、`targets` に `riscv64gc-unknown-none-elf`、`components` に `clippy` と `llvm-tools` を入れる
- 理由：版を固定しないと、`rustup update` のたびに警告や lint の挙動が変わり、レビューで見た状態と再現できなくなる
- できなくなること：新しい stable の機能は、ここを書き換えるまで使えない。上げるときは理由をここに追記する

### D-012：文字出力は SBI の Debug Console 拡張（DBCN）で行う

- 決定者：ユーザー
- 検討した案：DBCN ／ レガシー `console_putchar`（EID `0x01`）／ UART 16550 を直接叩く（xv6 の `uart.c` と同じ）
- 理由：この環境で動くことを確かめた（SPEC 5.1）。`ecall` 1 回で 1 文字が出るので、以降のすべての実演の土台になる出力を最も早く用意できる（WORKFLOW 4.7）。レガシー拡張は SBI 仕様で非推奨であり、M7 の実機で使えない可能性がある
- できなくなること：OpenSBI 1.2 より古いファームウェアでは文字が出ない。UART のレジスタを叩く経験は M6（受信割り込み）まで持ち越す。MMIO への volatile な書き込みは、D-013 の test デバイスで M0 のうちに経験する
- 補足：起動直後に `probe_extension` で DBCN の有無を確かめる手もあるが、確かめた結果を「出力できない」と伝える手段がない。M0 では確かめない

### D-013：QEMU の終了は、成功も失敗も test デバイス（`0x10_0000`）で行う

- 決定者：ユーザー
- 検討した案：test デバイスに一本化 ／ 成功は SBI の SRST、失敗は test デバイス
- 理由：SRST では失敗を終了コードとして伝えられないことを実測で確かめた（SPEC 6.1）。経路を 1 本にすれば、`cargo krun` の正常終了と `cargo ktest` の失敗が同じコードを通るため、片方の書き間違いが他方で見つかる
- できなくなること：QEMU 専用であり、実機では動かない。終了処理を 1 つの関数に閉じ込め、M7 でその中身だけを SRST に差し替える
- xv6 との違い：xv6 は QEMU を自分で終了させず、ループで止まる。本プロジェクトは自動テストの結果を終了コードで受け取るため、終了させる必要がある

### D-014：ビルド先のターゲットは `build.target` ではなく cargo エイリアスで指定する。リンカスクリプトは `kernel/build.rs` から渡す

- 決定者：アシスタント
- 内容：
  - `.cargo/config.toml` に `[build] target = ...` を書かない。`kernel` を RISC-V 向けにビルドするのは `krun`、`ktest` などのエイリアスが `--target riscv64gc-unknown-none-elf` を付けて行う
  - QEMU の起動は `[target.riscv64gc-unknown-none-elf] runner` に書く。`cargo run` と `cargo test` は、このターゲットの実行ファイルをこの runner に渡す
  - リンカスクリプトは `kernel/build.rs` が `cargo:rustc-link-arg=-T<絶対パス>` で渡す
- 理由：`build.target` を書くと `klib` のホスト向けテストまで RISC-V 向けになり、`cargo test -p klib` が動かない（パッケージごとにターゲットを変える `per-package-target` は nightly 専用で、D-009 により使えない）。リンカスクリプトを `rustflags` で渡すと相対パスがカレントディレクトリに左右されるが、`build.rs` なら `CARGO_MANIFEST_DIR` から絶対パスを組める。`kernel` 以外のクレートに渡ることもない
- できなくなること：リポジトリの直下で素の `cargo build` を打つと、`kernel` がホスト向けにビルドされて失敗する。`kernel` は必ずエイリアス経由でビルドする

### D-015：カーネルイメージのレイアウト（SPEC 4）

- 決定者：アシスタント
- 内容：セクションを `.text`、`.rodata`、`.data`、`.bss` の順に並べ、それぞれ 4 KiB 境界から始める。ブートスタックは 64 KiB とし、リンカスクリプトで `.bss` の後ろに確保する。0 クリアの範囲には入れない
- 理由：
  - 4 KiB 境界：M3 で、コードは R+X、読み取り専用データは R、それ以外は R+W とページ単位に権限を分ける。境界が揃っていないと、1 枚のページに 2 種類のセクションが乗り、どちらかの権限を緩めるしかなくなる
  - 64 KiB：xv6 はスタックを 1 ページ（4 KiB）にしているが、Rust のデバッグビルドは最適化されずスタックフレームが大きい。`core::fmt` を通る `println!` だけで数百バイトを使う。足りないとスタックが `.bss` を上書きし、離れた場所に症状が出る
  - 0 クリアの外：スタックは使う前に 0 である必要がない。`.bss` に入れると、起動のたびに 64 KiB を無駄に埋めることになる
  - `__global_pointer$` を定義しない：定義すると、リンカが `gp` 相対の命令に書き換える（relaxation）ことがある。`gp` を設定するまでそのコードが壊れるので、M0 では使わない
- できなくなること：スタックが溢れても検出されない。ガードページ（マップしないページを置いて溢れをページフォルトにする）は M3 以降でないと作れない。xv6 も同じ制約を持つ

### D-016：エントリはアセンブリのファイルに書き、`global_asm!` で取り込む。Rust 側の入口は `extern "C"` の `kmain`

- 決定者：アシスタント
- 内容：`kernel/src/entry.S` に `_start` を書き、`core::arch::global_asm!(include_str!("entry.S"))` で取り込む。`_start` は `.text.entry` セクションに置く。Rust 側の入口は `#[unsafe(no_mangle)] extern "C" fn kmain(hartid: usize, dtb: usize) -> !`
- 理由：
  - 別ファイル：Rust の文字列リテラルの中に命令を書くより、アセンブリとして読みやすい。コメントも `#` でそのまま書ける
  - `.text.entry`：リンカスクリプトで `.text` の先頭に固定できる。`ENTRY(_start)` だけでは、`_start` が `0x8020_0000` に来るとは限らない
  - `extern "C"`：Rust の通常の関数の呼び出し規約は仕様として決まっていない。アセンブリから呼ぶには、`a0`、`a1` に引数が入るという C の規約に固定する必要がある
  - `no_mangle`：Rust は関数名に情報を付け足した名前（mangle された名前）でシンボルを作る。アセンブリから `call kmain` と書けるように、名前をそのまま残す
- できなくなること：アセンブリの中から Rust の定数を `const` オペランドで参照できない（`include_str!` で取り込んだ文字列にはオペランドを書けない）。スタックの大きさなどの値は、リンカスクリプトのシンボルを経由して渡す

### D-017：文字出力は DBCN の `write_byte`（FID 2）で 1 バイトずつ送る

- 決定者：アシスタント
- 検討した案：`write_byte`（FID 2、1 バイトを引数で渡す）／ `console_write`（FID 0、バッファの**物理アドレス**と長さを渡す）
- 理由：`console_write` は、渡すアドレスが物理アドレスでなければならない。M3 でページングを有効にしたあと、仮想アドレスから物理アドレスへの変換を挟む必要が出る。`write_byte` は値だけを渡すので、ページングの前後で変わらない
- できなくなること：1 文字ごとに `ecall` で M モードとの間を往復するため、遅い。長い出力（M6 のシェル）で気になったら、`console_write` か UART への直接書き込みに切り替える

### D-018：SBI のエラーコードの解釈は `klib` に置く。`ecall` そのものは `kernel` に置く

- 決定者：アシスタント
- 内容：`klib::sbi` に、SBI のエラーコード（`isize`）を Rust の型に変換する部分を置き、ホストでテストする。`kernel::sbi` は、`ecall` を発行して `a0` と `a1` を受け取るだけにする
- 理由：エラーコードの表は、ハードに依存しない純粋な変換である（D-006、D-010）。数字の打ち間違いは、仕様の表と照らした固定値のテストで捕まえる（WORKFLOW 4.5、5.6）
- できなくなること：`kernel` が `klib` に依存するようになる。`kernel/Cargo.toml` に `klib = { path = "../klib" }` が要る
