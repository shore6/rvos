# 開発ワークフロー

仕様書：[SPEC.md](SPEC.md) ／ ロードマップ：[ROADMAP.md](ROADMAP.md) ／ 設計判断：[DECISIONS.md](DECISIONS.md)

本書は、このプロジェクトを「ユーザーの学習を通じて進める」という方針を、実際の手順と注意点として書き下したものである。

方針そのものは [CLAUDE.md](../CLAUDE.md) に置く。
本書はその運用、すなわち「毎回どういう順番で何をするか」「どこで失敗しやすいか」を扱う。

この進め方は、前のプロジェクト（どうぶつしょうぎライブラリ、C++）で効果が確かめられたものを引き継いでいる。
本書に出てくる「前プロジェクトの事例」はそこで実際に起きたことである。
本プロジェクトで起きた事例は、起きた時点で各節に書き足す。

## 1. 役割分担

| | 担当 |
| --- | --- |
| コードを書く | ユーザー |
| 設計・API の決定・選択肢の提示 | アシスタント |
| レビュー | アシスタント |
| ドキュメントの更新 | アシスタント |
| テストの観点の提示 | アシスタント |
| テストコードを書く | ユーザー |

**アシスタントは完成したコードを書いて渡さない。**
これは効率のための制約ではなく、目的そのものである。
ユーザーが書いて詰まり、指摘を受けて直す過程が、このプロジェクトの成果物の半分を占める。

ただし、レビューの中で**数行の断片**を示すのは構わない。
「`>=` に直す」「`?` を足す」のように、直す内容が一意に決まる箇所は、文章で説明するより短いコードで示した方が速く、学習の妨げにもならない。
関数まるごと、あるいはファイルまるごとを書くのは方針違反である。

境目の目安は「その断片を写しても、その関数の設計判断は残っている」かどうかである。

### 1.1 記法そのものは示してよい

カーネル開発には、Rust の入門書に出てこない記法が多い。
`asm!` のオペランドの書き方、`#[unsafe(no_mangle)]`、`global_asm!`、リンカスクリプトの `PROVIDE` など。

これらは**記法の見本**として示してよい。
たとえば「CSR を読むには `asm!("csrr {}, scause", out(reg) x)` と書く」は記法の説明であり、
「トラップの入口でどのレジスタをどの順に保存するか」は設計判断である。
前者は示し、後者はユーザーに書かせる。

アセンブリで書く部分（エントリ、トラップの入口、コンテキストスイッチ）は特に詰まりやすい。
設計ブリーフで「何をどの順番で行うか」を箇条書きにして渡し、命令列はユーザーが組む。

## 2. 1 ファイルあたりのサイクル

```
設計ブリーフ  →  ユーザーが実装  →  レビュー  →  修正  →  （必要なら再レビュー）  →  次のファイル
                                      ↓
                              設計判断が出たら DECISIONS.md
```

### 2.1 設計ブリーフ

ファイル（または小さなまとまり）に着手する前に、次を示す。

- **そのファイルが何を担うか**、依存関係のどこに位置するか
- **公開する API の一覧**（シグネチャまで。中身は書かない）
- **決めておくべき表現**（構造体の配置、ビットの割り当て、エラーの返し方、どの関数を `unsafe fn` にするか）
- **ハードウェアとの約束**：そのファイルが触るレジスタや CSR、その仕様の出典（RISC-V 特権仕様の節、SBI 仕様の拡張名、QEMU `virt` のアドレス）
- **つまずきやすい点**を先回りで 2〜4 個
- **テストで確認すべき観点**と、それを `klib`（ホスト）と QEMU のどちらで確かめるか

分量は多くてよい。実装の指示ではなく、実装のための地図である。

Rust の記法と標準ライブラリの知識に穴があることを前提にする。
`no_std` で使えるもの（`core` と `alloc`）と使えないもの（`std`）の区別、
`&mut` を 2 つ同時に持てない理由とその回避の仕方、
`static` と `static mut` の違い、`unsafe` が何を許して何を許さないか、
といった説明は毎回入れてよい。

ツール（cargo の設定、リンカスクリプト、QEMU のオプション、gdb）は前提知識ゼロとして扱い、必要な操作をそのまま示す。

### 2.2 選択肢の提示

設計上の分岐は、**選択肢を並べて推奨を明示する**形で出す。

- 案は 2〜3 個。それ以上は判断を助けない
- 各案について「何ができなくなるか」を書く。利点だけの比較は選べない
- 推奨を 1 つ決めて、その理由を書く
- xv6 がどちらを選んでいるかと、その理由を添える。xv6 と違う案を推すときは、違える理由を書く
- 決まったら **その場で** DECISIONS.md に記録する

「どちらでもよい」で終わらせない。
どちらでもよい選択なら、アシスタントが決めて通知するだけでよい。

### 2.3 ドキュメントの更新

**ユーザーに投げない。** 設計判断が出た瞬間に更新する。

| 出来事 | 更新先 |
| --- | --- |
| 表現・メモリ配置・ABI を決めた | SPEC.md |
| 「なぜそう決めたか」が残る決定をした | DECISIONS.md |
| マイルストーンが完了した | ROADMAP.md |
| ビルド・実行・デバッグの手順が変わった | BUILD.md |
| 外部クレートを追加した | DECISIONS.md（D-005 の方針に照らした理由） |

決定を**変更**したときは、変更後の内容だけを書かず、
「当初はこうだったが、こういう理由で変えた」を残す。

## 3. レビューの方法

前プロジェクトで最も効果が出た部分であり、最も手間がかかる部分でもある。

### 3.1 主張せず、実演する

「ここはバグっている」と書くだけでは伝わらない。
スクラッチパッドに切り出してビルドし、実際に走らせて出力を見せる。

前プロジェクトの事例。

```
[gle/1c1/1C1/ELG b - 1] -> nullopt
```

この 1 行があると、「`/` の分岐に `continue` がないので正しい SFEN が全部弾かれる」という説明が一読で腑に落ちた。
実演のない指摘は、正しくても納得されにくく、直し忘れが起きる。

カーネルでは、実演の手段がいくつかある。対象に応じて使い分ける。

| 対象 | 実演の手段 |
| --- | --- |
| `klib` のロジック | ホストのスクラッチクレートに切り出し、`cargo test` や `println!` で見せる |
| 起動・トラップ・割り込み | QEMU の出力。必要なら `-d int,guest_errors` でトラップの発生を記録させる |
| レジスタやメモリの中身 | QEMU を `-s -S` で止めて gdb をつなぎ、ブレークポイントで値を見せる |
| リンクの結果 | `rust-objdump -d` や `rust-nm` で、シンボルのアドレスや生成された命令を見せる |
| ハードの配置 | `-machine dumpdtb=` で QEMU の DTB を取り出し、`dtc` で読める形にして見せる |

ハングや無限のトラップのように「何も出ない」失敗は、観測できる形に加工する。
トラップの入口に一時的な文字出力を入れる、QEMU の `-d int` で例外の連続を見せる、gdb で `sepc` を読む、など。

アシスタントは、自分の作業環境にユーザーと同じツール一式（BUILD.md の手順）を入れて実演する。
それができない環境では、ユーザーに実行してほしいコマンドを 1 行で示し、出力を貼ってもらう。
その場合も「こう出るはずだ」と予想を先に書いておき、予想と違えばそれを報告する。

### 3.2 コンパイルエラーは「原因の数」で数える

12 個のエラーが出ていても、原因が 4 種類なら 4 項目として提示する。
前プロジェクトでは、`Position::` の書き忘れ 1 件が 9 個のエラーを生んだ。

Rust では、借用検査のエラーが連鎖しやすい。
1 つの `&mut` の持ち方が、離れた場所に何個ものエラーを出す。
型推論が 1 か所で失敗すると、その値を使う全箇所にエラーが出る。

エラーメッセージを上から順に列挙するのは、レビューとしては何もしていないに等しい。
**どれが原因で、どれが波及か**を分けるのがレビューの仕事である。

借用検査のエラーには、エラーの直し方だけでなく、
「コンパイラが何を心配しているか」（その書き方を許すとどんな壊れ方があり得るか）を添える。
ここを飛ばすと、`clone()` や `unsafe` で黙らせる癖がつく。

### 3.3 コンパイルエラーの裏に論理バグが隠れている

ビルドが通らない状態のコードには、コンパイルエラーに隠れて論理バグが同居していることが多い。

有効な手順は次のとおり。

1. ユーザーのファイルをスクラッチパッドにコピーする
2. **機械的な修正だけ**を当てる（綴り、型、`use` の抜け、可視性）
3. 動く状態にして、実際の入力を通す
4. 出てきた論理バグを、コンパイルエラーとは別立てで報告する

前プロジェクトでは、この手順で SFEN パーサから 5 件の論理バグを一度に洗い出した。

### 3.4 提示の順序

重い順に並べる。優先度は「正しさ」→「安全性」→「設計」→「書き方」。

1. 未定義動作：健全でない `unsafe`、エイリアスする `&mut`、未初期化の読み出し、範囲外のポインタ
2. ハードとの約束違反：保存し忘れたレジスタ、`sfence.vma` の抜け、割り込み禁止の抜け、volatile でない MMIO アクセス
3. 誤った結果を返す
4. 検査の抜け（特にユーザー空間から来た値）
5. 重複・責務の混在
6. 綴り、未使用の `use`、命名

1 と 2 は、多くの場合「今は動く」。だからこそ先頭に置く。
カーネルでは、未定義動作がずっと後の、関係のない場所で症状を出す。

各項目は「何が起きるか」「なぜそうなるか」「どう直すか」の 3 点を揃える。
「どう直すか」だけを並べたリストは、写して終わりになる。

### 3.5 良かった点を先に短く書く

3.4 の順序で並べると指摘だけが並ぶので、冒頭に確認できた事実を置く。
「`.bss` の初期化は境界シンボルどおりに動いている」「トラップから正しく復帰している」のように、
**検証した結果として**書く。褒め言葉ではなく、レビュー範囲の報告として扱う。

## 4. テストの扱い

### 4.1 「テストが緑」は「検証できている」ではない

前プロジェクトで実際に起きたこと。

- アサーションが 1 つもない空のテストが、`22/22 パス` の中に紛れていた
- 盤面を書き換える関数からビットボードの更新を丸ごと削っても、既存のテストは全部通った
- 表示関数の分岐のうち、一部の経路が一度も実行されていなかった

**カバレッジではなく、テストを壊す側から測る。**

### 4.2 テストの置き場所（D-006）

テストは 2 か所で動かす。

| 置き場所 | 対象 | 実行 |
| --- | --- | --- |
| `klib`（ホスト） | ハードに依存しないロジック：DTB の解析、アロケータ、ページテーブルの計算、ELF の解析、システムコールの引数検査 | `cargo test -p klib`。速く、何度でも回せる |
| `kernel`（QEMU） | ハードとの境界：起動、トラップ、割り込み、ページングの有効化、コンテキストスイッチ、ユーザーモード | `cargo ktest`。起動に時間がかかる |

**ロジックをハードから切り離せるなら、`klib` に置く。**
これは設計の方針でもある。
「物理アドレスのページを読む」部分を差し替えられる形にしておけば、ページテーブルの操作をホストのメモリ上で確かめられる。

QEMU 上のテストは、成功・失敗を QEMU の終了コードで返す（M0 で方式を決める）。
「何も出ずにハングした」も失敗として扱えるように、時間切れを設ける。

### 4.3 突然変異テスト

実装をわざと壊してテストが落ちるかを確認する。
落ちなければ、そのテストはその箇所を検証していない。

```
1 か所書き換える → テストを実行する → 落ちるか見る
```

- `klib`：`cargo-mutants` で機械的に回せる。導入するかは M2 で試して決める
- `kernel`：QEMU の起動が挟まるため遅い。`sed` で 1 か所ずつ手で書き換え、重要な箇所に絞る

前プロジェクトの M1 では 19 通りの変異を当て、生き残る変異が 11 件から 2 件に減るまでテストを足した。
どの検査が実際に効いているかが分かるので、テストの追加が当てずっぽうでなくなる。

### 4.4 殺せない変異を区別する

生き残る変異が、すべてテスト不足を意味するわけではない。**原理的に観測できない変異**が混ざる。
カーネルではこれが特に多い。

- **タイミング依存**：割り込み禁止の抜けは、その数命令の間に割り込みが来たときだけ壊れる。QEMU の `-icount` で再現しやすくはなるが、確実ではない
- **QEMU が寛容な箇所**：`sfence.vma` の抜けや、一部の不正なアクセスは、QEMU 上では症状が出ないことがある。実機では壊れる
- **単一 hart で隠れるもの**：メモリ順序（`fence`）の抜けは、hart が 1 つの間は観測できない（D-008）
- **防御的な検査**：今その状態を作る経路が存在しない

これらは「テストが足りない」ではなく「今の環境では観測できない」として、
理由と、代わりにどう守っているか（レビュー、`debug_assert!`、仕様の出典）とともに SPEC.md の「観測できない変異」の節に記録する。
区別せずにカバレッジを追うと、意味のないテストを書くことになる。

### 4.5 検証の錨を 1 本置く

往復テスト（符号化 → 復号 → 符号化）は、両側が**同じだけずれていれば**通ってしまう。
前プロジェクトでは、SFEN の出力を固定文字列と比べるテスト 1 本だけが、両側に逆向きのずれを入れる変異を検出した。

本プロジェクトでも同じ形が出てくる。

- PTE の符号化と復号 → 仕様書どおりの固定のビット列と比べるテストを添える
- 仮想アドレスの分解（VPN[2]、VPN[1]、VPN[0]、オフセット）と組み立て → 手計算した値で押さえる
- システムコールの引数の詰め方と取り出し方 → ユーザー側とカーネル側が同じ間違いをしても通ってしまう。番号を固定値で押さえる

**往復テストには必ず、片側だけを固定値で押さえるテストを添える。**
固定値の出典（RISC-V 特権仕様の図、QEMU の DTB の実物）をテストのコメントに書く。

### 4.6 異常系は拒否理由ごとに 1 つ

1 つの入力が複数の理由で拒否されると、そのうち 1 つの検査を消してもテストが落ちない。

DTB や ELF の解析、システムコールの引数検査では、拒否理由の一覧を作り、
各理由について**他の理由では拒否されない入力**を用意する。
その一覧は SPEC.md に置く。

### 4.7 実装の順序でテストを助ける

依存の少ない側、検証しやすい側から書かせる。

- 出力（文字表示）を最初に作る。以降のすべての実演の土台になる
- トラップの表示を、ページングより先に作る。ページングの失敗はトラップとして現れる
- ページテーブルの操作は、`klib` でホストのテストを通してから、カーネルで有効にする
- ELF ローダは、ホストのテストで実物の ELF（`user/` のビルド成果物）を読めるようにしてから、カーネルに組み込む

逆順にすると、「何も出ずに止まる」状態で原因を探すことになる。

## 5. 繰り返し出てくる注意点

### 5.1 `unsafe` の安全条件は呼ぶ側で守る

`unsafe fn` には、呼ぶ側が守るべき条件を `# Safety` として書く。
`unsafe` ブロックには、その条件がなぜ満たされているかを `// SAFETY:` として書く。

レビューでは、`// SAFETY:` の文章が**本当に成り立っているか**を確かめる。
「このアドレスは有効」と書いてあれば、誰がそれを保証しているかを辿る。

前プロジェクトの事例。
「範囲の保証は呼び出し側の責任」と決めた関数を、呼ぶ側が枚数を確かめずに呼び、
2 ビットのフィールドが隣に繰り上がって、**下流の整合性検査をすり抜けた**。

カーネルでは、契約違反の結果がメモリ破壊になる。
「下流で弾かれるはず」は根拠にならない。契約は呼ぶ側で守る。

`unsafe` は小さく保つ。
`unsafe` な操作（MMIO、CSR、生ポインタ）は小さな関数に閉じ込め、その外側は安全な API にする。

### 5.2 警告を無視しない

次を有効にする（M0 で設定する）。

- `cargo clippy` を通す
- `#![deny(unsafe_op_in_unsafe_fn)]`：`unsafe fn` の中でも、`unsafe` な操作に `unsafe` ブロックを要求する
- edition 2024 の `static_mut_refs`：`static mut` への参照を作ると拒否される

前プロジェクトでは、警告が論理バグを 4 種類捕まえた（型の取り違え、空のテスト、意図しないコピー、符号の混在）。
ビルド出力に警告が残っている状態で「動いた」としない。

### 5.3 型の取り違えをコンパイルエラーにする

前プロジェクトでは、駒と駒種の比較が警告で済み、片方の手番の駒だけ黙って弾かれる事故があった。

本プロジェクトで最も取り違えやすいのは、**物理アドレスと仮想アドレス**である。
どちらも `usize` で表せてしまい、取り違えても動くことがある（恒等写像の間は特に）。
`PhysAddr` と `VirtAddr`、ページ番号の `PhysPageNum` と `VirtPageNum` を別の型（newtype）にして、混同をコンパイルエラーにする。

ただし一律にはしない。
ビット演算や配列の添字として整数の性質を使う場所では、変換の手間が読みやすさを損なう。
newtype にするかは、取り違えたときの被害と変換の頻度で決め、DECISIONS.md に残す。

### 5.4 無効値の居場所

失敗を表す方法を、型に応じて使い分ける。

| 場面 | 表し方 |
| --- | --- |
| 値がないことがある | `Option<T>` |
| 失敗の理由を伝える | `Result<T, E>`（`E` は理由ごとの列挙型） |
| null にならないポインタ | `NonNull<T>`。`Option<NonNull<T>>` は生ポインタと同じ大きさになる |
| システムコールの戻り値 | ABI で決める（負の値をエラーにする、など）。M5 で SPEC.md に書く |
| 回復できない | `panic!`。カーネル内の矛盾に限る。ユーザーの入力で panic させない |

**ユーザー空間から来た値で、カーネルを panic させない。** これは M5 の完了条件である。

### 5.5 出力の宛先

コンソールには、カーネルのログと、ユーザープログラムの出力と、テスト結果が同じ 1 本の UART に流れる。

前プロジェクトでは、CLI の標準出力にデバッグ用の出力が残り、
**解析に失敗して終了コード 1 を返しているのに標準出力に 6 行出ている**状態になっていた。

本プロジェクトでは次を守る。

- デバッグ用の一時的な出力は、作業が終わったら消す。残すなら、ログの重要度で絞れるようにする
- テストの結果は、終了コードで判定する。出力の文字列を見て判定しない
- M6 以降、シェルの画面にカーネルのログが割り込まないようにする

判断の基準は「この出力を、いつも見たいか」である。

### 5.6 仕様の出典を書く

ハードウェアの値（CSR のビット位置、PTE のフラグ、SBI の関数番号、MMIO のアドレス）は、記憶で書かない。
コードのコメントに出典（仕様書の名前と節、または DTB）を書き、レビューではその出典と照らし合わせる。
数字の打ち間違いはテストで捕まえにくい。テストを書く人も同じ記憶に頼るからである。

## 6. この方式のコスト

レビューに実演を伴うため、1 ファイルあたり数往復かかる。
カーネルでは、QEMU と gdb を使う実演が加わるため、前プロジェクトよりさらに手間がかかる。

その代わり、前プロジェクトでは最初のマイルストーンを終えた時点で次が得られた。

- ソースの論理バグ 11 件（うち未定義動作 1 件）を、テストが書かれる前に除去
- テストの穴 11 件を突然変異テストで特定し、2 件（いずれも観測不能）まで削減
- 設計判断 15 件が理由とともに記録され、後から覆せる状態

カーネルの未定義動作は、後になって関係のない場所で症状を出す。
早い段階で除去しておく価値は、前プロジェクトより大きい。

速度を上げたい場合に削ってよいのは 3.1（実演）ではなく、設計ブリーフの網羅性である。
実演を省くと、指摘が伝わらず同じバグが再発する。

## 7. 出力スタイルとの関係

セッションが「Learning」出力スタイルで動作している場合、
`★ Insight` ブロックによる補足と、`TODO(human)` を置いて実装を依頼する「Learn by Doing」の仕組みがある。

本プロジェクトでは **`TODO(human)` 方式は使わない。**
全コードをユーザーが書くため、依頼すべき箇所を特定する必要がないからである。
設計ブリーフ（2.1）がその役割を果たす。

`★ Insight` は使う。
ただし一般的な解説ではなく、**このコードベースに固有の事実**を書く。
「なぜカーネルを `0x8020_0000` に置くのか」は書く価値があるが、「ページングとは」は書かない。
