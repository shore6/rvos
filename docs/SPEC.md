## 2. 物理メモリの配置（QEMU `virt`）

**確認済み（2026-11-08、M0 着手時）**：QEMU 8.2.2 の `-machine virt,dumpdtb=virt.dtb -smp 1 -m 128M` で取り出した DTB と照らし合わせ、下表のアドレスはすべて一致した（手順は BUILD.md 5.4）。
M2 以降は、DTB から読んだ値を正とする。

| アドレス | 大きさ | 内容（DTB の `compatible`） | 使い始め |
| --- | --- | --- | --- |
| `0x0010_0000` | `0x1000` | test デバイス（`sifive,test1`、`sifive,test0`、`syscon`）。QEMU の終了に使える | M0（候補） |
| `0x0010_1000` | `0x1000` | RTC（goldfish） | 使う予定なし |
| `0x0200_0000` | `0x1_0000` | CLINT（タイマー、ソフトウェア割り込み） | 直接は触らない予定（SBI 経由） |
| `0x0c00_0000` | `0x60_0000` | PLIC（外部割り込みコントローラ） | M6 |
| `0x1000_0000` | `0x100` | UART0（`ns16550a`） | M0 または M6 |
| `0x1000_1000` 〜 `0x1000_8000` | 各 `0x1000` | virtio-mmio デバイス 8 個 | M7 以降 |
| `0x8000_0000` | `0x800_0000`（128 MiB） | RAM。先頭に OpenSBI が置かれる（`Firmware Size : 322 KB`） | ― |
| `0x8020_0000` | ― | カーネルの読み込み先・開始アドレス | M0 |

RAM の大きさは QEMU の `-m` で決まる（既定は 128 MiB）。

同じ DTB から読めた、後のマイルストーンで効く値。

| 項目 | 値 | 効くところ |
| --- | --- | --- |
| `timebase-frequency` | `0x989680`（10 MHz） | M1 のタイマー間隔 |
| `riscv,isa` | `rv64imafdch_..._sstc_svadu` | Sstc があるため、M1 で `stimecmp` を直接書く案が取れる |
| `mmu-type` | `riscv,sv57` | QEMU の既定。Sv39 も使える（M3） |

## 3. 起動時の約束（OpenSBI → カーネル）

OpenSBI がカーネルへ制御を渡すときの状態。
M0 で実際に確かめ、違いがあれば書き換える。

**確認済み（2026-11-08）**：`-kernel` に ELF を渡したときの OpenSBI のバナーで、`Domain0 Next Address : 0x0000000080200000`、`Domain0 Next Mode : S-mode` を確認した。
`Domain0 Next Arg1`（DTB のアドレス）は `0x87e0_0000`（RAM の末尾付近）だった。
**gdb で確認済み（2026-11-10）**：使い捨てイメージを `-s -S` で起動し、`b *0x80200000` で止めてレジスタを読んだ（手順は BUILD.md 5.2）。下表の「実測」の列がその値である。

| 項目 | 状態 | 実測 |
| --- | --- | --- |
| 開始アドレス | `0x8020_0000`（`pc`） | 一致 |
| 特権モード | S モード | バナーの `Next Mode` で確認 |
| `a0` | 起動した hart の ID | `0x0` |
| `a1` | DTB の物理アドレス | `0x87e0_0000` |
| `satp` | 0（ページングは無効） | `0x0` |
| 割り込み | 無効 | `sstatus` = `0x8000_0002_0000_6000`。SIE（ビット 1）は 0 |
| 浮動小数点 | 有効 | 同じ `sstatus` の FS（ビット 13〜14）が `11`（Dirty） |
| スタック | **使えない値が入っている**。カーネルが自分で用意する | `sp` = `0x8004_6eb0`。OpenSBI の M モード専用領域（`0x8004_0000`〜`0x8005_ffff`、S/U からは権限なし）を指す |
| `.bss` | 0 クリアされている保証はない。カーネルが自分で埋める | QEMU では RAM が最初から 0 だった（`0x8030_0000` と `0x8400_0000` を読んで確認） |

注意点が 2 つある。

- `sp` は 0 ではなく、もっともらしい値が入っている。設定し忘れても最初の数命令は動き、スタックに積んだ時点で**アクセス例外**になる。「スタックを使うまでは動く」という壊れ方をする
- QEMU では RAM が 0 から始まるため、`.bss` の 0 クリアを忘れても QEMU 上では症状が出ない（WORKFLOW 4.4）。確かめるには、gdb で `.bss` を 0 以外の値で埋めてから先へ進める

## 4. カーネルイメージのレイアウト

M0 ステップ 2 で決めた（D-015）。リンカスクリプトは `kernel/linker.ld`。

```
0x8020_0000 ┬ __text_start
            │ .text       先頭に .text.entry（_start）を置く
            ├ __text_end    （ここから 4 KiB 境界）
            ├ __rodata_start
            │ .rodata
            ├ __rodata_end
            ├ __data_start  （4 KiB 境界）
            │ .data  .sdata
            ├ __data_end
            ├ __bss_start   （4 KiB 境界）
            │ .bss   .sbss   _start が 0 で埋める範囲
            ├ __bss_end     （8 バイト境界）
            ├ __boot_stack_bottom （4 KiB 境界）
            │ ブートスタック 64 KiB。0 クリアしない
            ├ __boot_stack_top    （16 バイト境界）
            └ __kernel_end  （4 KiB 境界）
```

| 決まりごと | 値 |
| --- | --- |
| セクションの順序 | `.text` → `.rodata` → `.data` → `.bss` → ブートスタック |
| 各セクションの先頭 | 4 KiB 境界（M3 でページ単位に権限を分けるため） |
| `__bss_start`、`__bss_end` | 8 バイト境界（`_start` が `sd` で 8 バイトずつ埋めるため） |
| ブートスタックの大きさ | 64 KiB（`0x1_0000`） |
| `__boot_stack_top` | 16 バイト境界（RISC-V の呼び出し規約が `sp` に要求する） |
| `__kernel_end` | 4 KiB 境界。M2 の物理ページアロケータはここから使う |
| `.sdata`、`.sbss` | `.data`、`.bss` に含める。`__global_pointer$` は定義しない |

観察（2026-11-12）：rustc 1.99.1 は、`static mut X: u32` を `.bss` に、`static X: u64` を `.rodata` に置いた。small data のセクション（`.sdata`、`.sbss`、`.srodata`）は出していない。
リンカスクリプトに書いておくのは、C のオブジェクトや将来のコンパイラが出したときの備えである。

M0 着手時の観察（2026-11-08）：リンカスクリプトを使わず `-Ttext=0x80200000` だけで ELF を作ると、ELF ヘッダと program header を載せた LOAD セグメントが `0x1_0000`（RAM の外）にでき、カーネルの文字出力が一度も出ないまま止まった（どこで止まったかは未調査）。
リンカスクリプトで配置を明示すれば、LOAD は `0x8020_0000` からの 1 本だけになり、正しく起動した。
セクションの順序、各境界のシンボル名、ブートスタックの大きさと置き場所をここに書く。

## 5. SBI の利用

使う拡張と関数（文字出力、タイマー、終了）を、拡張 ID と関数 ID とともにここに書く（M0、M1 で決める）。

### 5.1 この環境の SBI 実装（確認済み、2026-11-08）

QEMU 8.2.2 同梱の **OpenSBI v1.3**。バナーの `Runtime SBI Version` は **1.0**。
スクラッチパッドの使い捨てイメージから `ecall` を発行し、次を確かめた。

| 確かめたこと | 結果 |
| --- | --- |
| レガシー `console_putchar`（EID `0x01`） | 文字が出る |
| Base 拡張 `probe_extension`（EID `0x10`、FID `3`）で DBCN（EID `0x4442_434E`）を問い合わせ | 1（あり）。SBI 1.0 を名乗るが、OpenSBI 1.3 は DBCN を実装している |
| DBCN `write_byte`（FID `2`） | 文字が出る |
| Base 拡張で SRST（EID `0x5352_5354`）を問い合わせ | 1（あり） |

`ecall` の呼び出し規約：`a7` に EID、`a6` に FID、`a0`〜`a5` に引数。戻り値は `a0` がエラーコード、`a1` が値（SBI 仕様 v2.0 第 3 章）。
レガシー拡張だけは `a6` を使わず、戻り値も `a0` だけである。

## 6. QEMU の起動オプションと終了コード

### 6.1 終了コードの伝わり方（確認済み、2026-11-08）

使い捨てイメージで、QEMU のプロセスの終了コードを実測した。

| カーネルがしたこと | QEMU の終了コード |
| --- | --- |
| test デバイス（`0x10_0000`）に 32 ビットで `0x5555` を書く | 0 |
| test デバイスに `0x3333 \| (3 << 16)` を書く | **3** |
| SRST `system_reset`（type = 0 shutdown、reason = 0 理由なし） | 0 |
| SRST `system_reset`（type = 0 shutdown、reason = 1 system failure） | **0**（失敗が伝わらない） |

OpenSBI 1.3 の SRST は、shutdown の理由を test デバイスに伝えず、常に成功として終わる。
**失敗を終了コードとしてホストへ伝えられるのは test デバイスだけ**である。

### 10.3 観測できない変異

突然変異テストで生き残り、かつ今の環境では原理的に観測できない変異を、理由と代わりの守り方とともにここに書く（WORKFLOW 4.4）。

#### M0 ステップ 2：`entry.S`（2026-11-12）

`entry.S` に手で変異を当て、gdb で `kmain` まで進めた。あわせて `-d int` でトラップを記録した。

| 変異 | 観測できたか | 現れ方・理由 | 代わりの守り方 |
| --- | --- | --- | --- |
| `la sp` を削除 | **できた** | `kmain` の最初の `sd` で store access fault（cause 7、`tval` は OpenSBI の領域 `0x8004_6ea0`）。そのあと同じ例外が 1 万回以上続く | M1 以降はトラップの表示で直接見える |
| `a0` を一時レジスタに使う | gdb でのみ | `kmain` の `hartid` が `0x8020_1008` になる。ステップ 3 で hart ID を表示すれば、出力で見える | ステップ 3 の表示 |
| `.bss` の 0 クリアを丸ごと削除 | **できない** | QEMU の RAM が最初から 0 である（SPEC 3） | gdb で `.bss` を `-1` で埋めてから `kmain` まで進め、0 になっていることを見る手順（BUILD.md 5.2） |
| `sp` に `__boot_stack_bottom` を入れる | **できない**（今は） | `sp` が `.bss` の直前になり、`kmain` のフレームが `.bss` と `.text` の後ろの余白に書かれる。今の `.bss` には、壊れて困る値がない | レビュー。M1 以降、`.bss` に置いた値が化けたときはここを疑う |
| 0 クリアが `__bss_end` を越えて書く（`__bss_end` が 8 の倍数でない） | **できない**（今は） | 越えた先は、ブートスタックの手前の余白で、誰も使っていない。レビューで、`.bss` を 4 バイトにした版を作って実際に起きることを確かめ、リンカスクリプトを直した | `__bss_end` を 8 バイト境界に揃える（SPEC 4）。gdb で `__bss_end` の直後に `-1` を書いて確かめる |

同じレビューで、リンカスクリプトの境界のシンボルは「今の大きさでは偶然揃う」ことがわかった（`.bss` が 0 バイト、スタックが 64 KiB ちょうど）。
リンカスクリプトを変えたときは、`.bss` に 4 バイトの `static` を足した版と、スタックを `64K + 0x10` にした版で、`rust-nm -n` を見て境界を確かめる。
