# 開発ロードマップ

仕様書：[SPEC.md](SPEC.md) ／ 設計判断：[DECISIONS.md](DECISIONS.md)

## 進め方

各マイルストーンは「動く状態」で区切る。
一つ終えるごとに QEMU 上で結果を確認でき、テストが通る状態を保つ。

各マイルストーンには、参照先 xv6-riscv で対応するファイルを添える。
読むのは構造と理由であり、コードは写さない（D-004）。
xv6 は M モードから自前で起動するが、本プロジェクトは OpenSBI に任せるため（D-002）、`start.c` に当たる部分はない。

hart（RISC-V の CPU コア）は M6 まで 1 つだけを使う（D-008）。
ロックや割り込み禁止は最初から正しく書くが、複数 hart での検証は M7 以降に回す。

## M0：土台

**目標**：自作カーネルが QEMU 上で起動し、文字を出して自分で QEMU を終了させる。

- cargo ワークスペースの構成（`kernel`、`klib` の 2 クレート）
- `rust-toolchain.toml` によるツールチェーンとターゲットの固定
- リンカスクリプト：カーネルを `0x8020_0000` に置き、各セクションの境界をシンボルで書き出す
- エントリ（`_start`）：アセンブリでスタックポインタを設定し、`.bss` を 0 で埋めて Rust の関数へ飛ぶ
- SBI 呼び出し（`ecall`）の薄い層と、それを使った文字出力
- `print!` / `println!` マクロと `#[panic_handler]`
- QEMU の終了と終了コード（成功と失敗を区別する）
- QEMU 上の統合テストの枠組みと、`klib` のホスト側テスト 1 件

**完了条件**：`cargo krun` で OpenSBI のバナーに続いて自作のメッセージが表示され、QEMU が終了する。
`cargo ktest` と `cargo test -p klib` が緑になる。失敗するテストを入れると `cargo ktest` が非 0 で終わる。

**設計判断**：文字出力の経路。
SBI の Debug Console 拡張（DBCN）を使うか、レガシーの `console_putchar` を使うか、UART（16550）のレジスタを直接叩くか。
SBI に任せれば数行で済むが、UART を叩く経験は M6 の受信割り込みで必要になる。

**設計判断**：QEMU の終了方法と、テスト失敗を終了コードとして取り出す方法。
SBI のシステムリセット拡張（SRST）を使うか、`virt` の test デバイスに書き込むか。
どちらで終了コードがホストに伝わるかは、実際に試してから決める。

**参照先**：`kernel/entry.S`、`kernel/kernel.ld`、`kernel/printf.c`

## M1：トラップとタイマー

**目標**：例外と割り込みを受け取り、何が起きたかを表示できる。

- `stvec` の設定とトラップの入口（アセンブリ）
- トラップフレーム：レジスタを保存する構造体と、その配置
- 例外の表示（原因 `scause`、発生アドレス `sepc`、付随値 `stval`）と `ebreak` からの復帰
- タイマー割り込み：一定間隔で割り込みを起こし、tick を数える
- 割り込みの許可と禁止（`sstatus.SIE`、`sie`）を包む関数

**完了条件**：不正なアドレスを読むと、原因とアドレスを表示して停止する。
`ebreak` を踏んでも処理が続く。タイマーの tick が一定間隔で進む。

**設計判断**：トラップフレームの置き場所と形。
xv6 はカーネル内のトラップでは現在のスタックに積み、ユーザーからのトラップでは専用のページに置く。
M1 の時点で、M5 のユーザートラップまで見越した形にするかどうかを決める。

**設計判断**：タイマーの設定方法。
SBI の `set_timer` を呼ぶか、Sstc 拡張の `stimecmp` に直接書くか。

**参照先**：`kernel/trap.c`、`kernel/kernelvec.S`

## M2：物理メモリとヒープ

**目標**：物理メモリをページ単位で配り、`Box` や `Vec` が使える。

- デバイスツリー（DTB）の解析：OpenSBI から渡されるアドレスを読み、メモリの範囲を得る
- 物理ページアロケータ：カーネルの末尾から RAM の終わりまでを 4 KiB 単位で管理する
- ヒープアロケータと `#[global_allocator]`、`alloc` クレートの有効化
- アロケータの割り当てと解放の検証

**完了条件**：DTB から得た RAM のサイズが表示される。
カーネル内で `Vec` に要素を積み、解放後に同じ量を再び確保できる。
DTB の解析とアロケータのロジックが `klib` のホスト側テストで検証されている。

**設計判断**：物理ページアロケータの方式。
空きページを連結リストでつなぐ方式（xv6 と同じ）と、ビットマップ方式がある。
連続した複数ページを確保できるか、管理情報をどこに置くかが違う。

**設計判断**：ヒープアロケータの方式。
自作の連結リスト方式、バディ方式、サイズ別のスラブ方式。ここは学習量と実装量の釣り合いで決める。

**設計判断**：DTB を自前で解析するか、メモリ範囲を QEMU の既定値で決め打ちするか。
DTB の解析は `klib` に置けばホストでテストでき、M6 で UART や PLIC の位置を得るのにも使える。

**参照先**：`kernel/kalloc.c`

## M3：仮想メモリ

**目標**：カーネル自身がページテーブルの上で動く。

- Sv39 のページテーブル：3 段のテーブル、PTE のビット、マップとアンマップ
- アドレスの型：物理アドレスと仮想アドレスを別の型にする（WORKFLOW 5.3）
- カーネル空間の構築：コード、データ、ヒープ、MMIO 領域のマップと権限の設定
- `satp` の切り替えと `sfence.vma`
- ページフォルトの表示（M1 のトラップを使う）

**完了条件**：ページングを有効にしたあともカーネルが動き続ける。
書き込み禁止のページに書くと、ページフォルトとして捕まる。
ページテーブル操作のロジックが `klib` のホスト側テストで検証されている。

**設計判断**：カーネル空間の配置。
物理アドレスと同じ仮想アドレスにマップする恒等写像（xv6 と同じ）か、上位アドレスに置く higher-half か。
恒等写像は単純だが、ユーザー空間と同じアドレス範囲を奪い合う。

**設計判断**：ページテーブル操作をホストでテストする方法。
物理メモリを直接触るコードをホストで動かすには、「物理アドレスからテーブルを引く」部分を差し替えられる形にする必要がある。

**参照先**：`kernel/vm.c`、`kernel/riscv.h`

## M4：カーネルスレッドとスケジューリング

**目標**：複数の処理が交互に動き、タイマーで強制的に切り替わる。

- タスク（スレッド）の構造体と、タスクごとのカーネルスタック
- コンテキストスイッチ：callee-saved レジスタの保存と復元（アセンブリ）
- ラウンドロビンのスケジューラ
- タイマー割り込みによるプリエンプション
- スピンロックと、ロック中の割り込み禁止（入れ子に対応する）

**完了条件**：3 つのタスクが文字を出しながら交互に進み、どのタスクも `yield` を呼ばなくても切り替わる。
タスクの生成と終了を繰り返しても、ページが漏れない。

**設計判断**：スケジューラの形。
xv6 のように専用のスケジューラ用コンテキストを経由するか、タスク同士で直接切り替えるか。

**設計判断**：割り込み禁止とロックの関係。
ロックを取っている間は割り込みを禁止する。入れ子の深さと、元の許可状態をどこに保存するか。

**参照先**：`kernel/proc.c`、`kernel/swtch.S`、`kernel/spinlock.c`

## M5：ユーザーモードとシステムコール

**目標**：U モードで動くプログラムが、システムコールで文字を出して終了する。

- ユーザー空間のページテーブルと、カーネル・ユーザー間のトラップの行き来（`sscratch`、`sret`）
- システムコールの ABI：番号と引数の渡し方、戻り値とエラーの表し方
- ユーザーのポインタの検査と、ユーザー空間からのコピー
- ELF ローダ：ユーザープログラムを読んでセグメントをマップする
- 最初のシステムコール：`write`、`exit`、`getpid`、`yield`
- `user/` クレート：ユーザープログラムとシステムコールのラッパー

**完了条件**：カーネルに埋め込んだユーザープログラムが U モードで起動し、`write` で文字を出し、`exit` で終わる。
ユーザープログラムが不正なアドレスを渡しても、カーネルは落ちずにそのプロセスだけを終わらせる。
ELF ローダが `klib` のホスト側テストで検証されている。

**設計判断**：ユーザー空間とカーネル空間の切り替え方。
xv6 のようにトランポリンページを使ってアドレス空間ごと切り替えるか、
ユーザーのページテーブルにカーネルを同居させて `sstatus.SUM` でユーザーのページに触るか。
前者は安全で xv6 に近く、後者は単純で速い。

**設計判断**：ユーザープログラムの置き場所。
M7 までディスクを持たないため、カーネルイメージに埋め込む（`include_bytes!`）。ビルドの順序をどう組むかを決める。

**参照先**：`kernel/trampoline.S`、`kernel/syscall.c`、`kernel/exec.c`、`user/usys.pl`

## M6：入力とシェル

**目標**：シェルにコマンドを打ち込み、ユーザープログラムを起動できる。

- PLIC（外部割り込みコントローラ）の設定
- UART の受信割り込みと、コンソールの入力バッファ
- `read` システムコールと、入力待ちでのプロセスの休止と起床
- プロセスの生成と待機：`spawn`（または `fork` / `exec`）、`wait`
- ユーザー空間の簡易シェル

**完了条件**：シェルからユーザープログラムを名前で起動し、その終了コードがシェルに表示される。
存在しない名前を打っても、シェルは落ちずに次の入力を待つ。

**設計判断**：プロセスの生成方式。
Unix 流の `fork` + `exec` か、新しいプロセスを直接作る `spawn` か。
`fork` はアドレス空間の複製が要り、`spawn` は引数の受け渡しが要る。

**設計判断**：休止と起床の仕組み（xv6 の `sleep` / `wakeup` に当たるもの）。
起床の取りこぼしを防ぐため、ロックとの関係を先に決める。

**参照先**：`kernel/plic.c`、`kernel/uart.c`、`kernel/console.c`、`user/sh.c`

## M7 以降：拡張（将来）

第 1 段階（M6）の完了後に、興味に応じて選ぶ。

- **virtio-blk**：QEMU の仮想ディスクの読み書き
- **ファイルシステム**：xv6 と同等の単純な FS。ユーザープログラムをディスクから読むようにする
- **パイプ**とファイルディスクリプタの一般化
- **マルチ hart**：複数のコアの起動と、ロックの検証
- **実機**：VisionFive 2 などの RISC-V ボードでの起動

## 依存関係

```
M0 ──> M1 ──> M2 ──> M3 ──> M4 ──> M5 ──> M6 ──> M7
```

順番に積み上がる。M2 の DTB 解析は M6 の PLIC・UART の位置を得るのにも使う。
